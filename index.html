Part I

Parity, RAID & Galois Fields

The mathematical foundations of fault tolerance: bitwise XOR parity, finite field Galois arithmetic, fast lookup tables, and Shannon entropy lower bounds.

01 Parity Invariants

Simple Parity, Hamming Distance & RAID-5 / RAID-6 Dual Parity

The simplest erasure code is single parity: given $k$ data disks $D_1, D_2, \dots, D_k$, compute the parity block as the bitwise exclusive OR:

$$P = D_1 \oplus D_2 \oplus \dots \oplus D_k$$

Because XOR is its own inverse ($A \oplus A = 0$), losing any single disk $D_i$ can be solved by XORing the surviving data blocks with $P$:

$$D_i = P \oplus \bigoplus_{j \ne i} D_j$$

However, RAID-5 cannot survive two concurrent drive failures. RAID-6 introduces a second parity drive $Q$, calculated using Galois Field multiplication to guarantee that any two arbitrary disk failures remain uniquely solvable.

02 Finite Fields

Abstract Algebra for Systems Engineers: Galois Fields $GF(2^8)$

Standard computer integer arithmetic wraps or overflows beyond 8, 16, or 64 bits. In storage systems, we need arithmetic where operations over 8-bit bytes always produce another 8-bit byte without overflow or precision loss. This mathematical structure is a Galois Field $GF(2^8)$.

In $GF(2^8)$:

  • Addition & Subtraction: Are identical and equal to bitwise XOR ($A + B = A \oplus B$). No carries!
  • Multiplication: Bytes are treated as polynomials with coefficients in $\{0, 1\}$. Polynomials are multiplied and reduced modulo an irreducible Primitive Polynomial: $P(x) = x^8 + x^4 + x^3 + x^2 + 1$ (hexadecimal 0x11D).
03 Lookup Tables

Galois Field Log/Antilog Tables & Bitmatrix Arithmetic

Computing polynomial division in software for every byte in a multi-gigabyte HDFS block would devastate CPU throughput. High-performance erasure coding libraries (James Plank's Jerasure, Intel ISA-L) use Logarithm and Antilog (Exponent) Lookup Tables.

Every non-zero element in $GF(2^8)$ can be generated as a power of a primitive generator $\alpha = 2$. Multiplication simplifies to integer addition modulo 255:

$$A \otimes B = \text{antilog}\big((\text{log}[A] + \text{log}[B]) \pmod{255}\big)$$

By keeping two 256-byte lookup tables resident in L1 CPU cache, Galois multiplication executes in $O(1)$ time with just three memory reads!

04 Information Theory

Information Entropy & Lossless Compression Lower Bounds

Claude Shannon's 1948 landmark paper established that information content is bounded by Shannon Entropy $H(X)$:

$$H(X) = -\sum_{i=1}^n p(x_i) \log_2 p(x_i)$$

Shannon's Source Coding Theorem mathematically proves that no lossless compression algorithm (gzip, snappy, zstd, lz4) can compress data below $H(X)$ bits per symbol on average. Data with uniform probability distributions (such as encrypted blocks or pre-compressed video) has $H(X) \approx 8.0\text{ bits/byte}$ and is mathematically incompressible.

Part II

Reed-Solomon Codes & Matrices

The industry standard for distributed storage fault tolerance: Vandermonde distribution matrices, Cauchy bitmatrices, and Gaussian elimination decoding.

05 Vandermonde Coding

Reed-Solomon Encoding: Vandermonde Distribution Matrix ($k \times m$)

In an $RS(k, m)$ code, $k$ data blocks are encoded into $k + m$ storage blocks. Any $m$ of the $k+m$ blocks can fail without losing a single byte of data. This is achieved via matrix multiplication:

$$\mathbf{C} = \mathbf{G} \cdot \mathbf{D}$$

The Generator Matrix $\mathbf{G}$ has dimensions $(k+m) \times k$. The top $k \times k$ submatrix is the Identity Matrix $\mathbf{I}_k$ (ensuring the original $k$ data blocks remain untouched), while the bottom $m \times k$ submatrix is a Vandermonde Matrix whose entries are powers of field generators $g_{i,j} = j^{i-1}$ over $GF(2^8)$.

06 Cauchy Bitmatrices

Cauchy Reed-Solomon Matrices & Eliminating Multiplications with XOR Bitmatrices

While Vandermonde matrices are conceptually elegant, inverting Vandermonde submatrices can occasionally encounter singular (non-invertible) configurations unless complex adjustments are made. Furthermore, field multiplications still consume precious CPU cycles.

Cauchy Reed-Solomon (Jerasure, James Plank) uses Cauchy matrices where every entry is defined as $a_{i,j} = \frac{1}{x_i \oplus y_j}$. Cauchy matrices are mathematically guaranteed to have every square submatrix non-singular. Furthermore, each field element is projected into an $8 \times 8$ binary bitmatrix, converting the entire Reed-Solomon encoding schedule into pure SIMD XOR operations (AVX-512 / ARM NEON)!

07 Erasure Decoding

Erasure Decoding: Inverting the Surviving Submatrix ($A^{-1} \cdot D'$)

When up to $m$ storage nodes crash, how does the storage engine reconstruct the lost data? By solving a linear system of equations:

  1. Identify any $k$ surviving nodes and select their corresponding rows from generator matrix $\mathbf{G}$ to form a $k \times k$ matrix $\mathbf{A}$.
  2. Invert matrix $\mathbf{A}$ over $GF(2^8)$ using Gaussian Elimination to obtain $\mathbf{A}^{-1}$.
  3. Multiply $\mathbf{A}^{-1}$ by the surviving data vector $\mathbf{D}'$ to reconstruct the original data vector $\mathbf{D} = \mathbf{A}^{-1} \cdot \mathbf{D}'$!
08 Zero-Copy IO

Systematic vs. Non-Systematic Codes & Direct Zero-Copy Data Passing

An erasure code is Systematic if the original input data appears verbatim and unencoded in the output codeword. If an erasure code were non-systematic, reading even a single uncorrupted file would require contacting $k$ nodes and running matrix inversion decoding on every read!

By enforcing systematic coding ($\mathbf{G} = [\mathbf{I}_k \mid \mathbf{P}]^T$), distributed storage engines (HDFS, Ceph, MinIO) serve normal client read requests directly from disk via zero-copy Linux kernel syscalls (sendfile() and splice()). Decoding math is executed *only* during active node failures.

Part III

Distributed Storage Codes (HDFS)

Production storage architectures in Hadoop HDFS 3.0: 1MB striped cell layouts, the degraded read network bottleneck, and Locally Repairable Codes (LRC).

09 HDFS 3.0 EC

HDFS Erasure Coding: Striping Cell Size (1MB) vs. Block Level EC

In traditional Hadoop HDFS, files were divided into large 128MB contiguous blocks. If erasure coding were applied at the block level, a small 10MB file could not fill $k=6$ blocks, forcing either massive zero-padding waste or falling back to 3x replication.

HDFS 3.0 introduced Striped Erasure Coding (RS-6-3-1024k). Logical blocks are divided into 1MB Cells. Cells are striped round-robin across 6 DataNodes plus 3 Parity nodes concurrently. This allows files of any size to leverage erasure coding while aggregating disk throughput across 6 independent DataNode network cards simultaneously!

10 Network Amplification

The Degraded Read Problem & Single-Disk Repair Network Penalty

While Reed-Solomon saves enormous disk space, it introduces a severe network penalty during background drive replacement: The Degraded Read Bottleneck.

In standard $RS(k, m)$, reconstructing a *single* lost block requires downloading $k$ surviving blocks across the datacenter network! For $RS(6, 3)$, repairing one 128MB block generates $6 \times 128\text{MB} = 768\text{MB}$ of cross-rack network traffic (a $6\times$ network amplification penalty). Because over 95% of datacenter storage incidents are single drive failures, standard RS floods top-of-rack network switches during routine rebalancing.

11 LRC Architecture

Locally Repairable Codes (LRC): Microsoft Azure & HDFS

To eliminate the degraded read network bottleneck, Microsoft Research developed Locally Repairable Codes (LRC), now adopted in Windows Azure Storage and Apache Hadoop HDFS.

LRC divides the $k$ data blocks into smaller local groups (e.g. $k=12$ split into two groups of 6) and computes a Local Parity block for each group, alongside 2 Global Parity blocks. When a single drive fails, the storage engine reads *only the 6 blocks within the local group* plus the local parity, slashing network reconstruction traffic by 50%!

12 Piggybacking Codes

Hitchhiker / Piggybacking Codes: Sub-Chunk I/O Savings in HDFS

Invented at UC Berkeley and CMU by K.V. Rashmi et al., Hitchhiker Codes reduce repair network traffic without adding extra parity storage overhead. Hitchhiker splits each block into two sub-chunks and "piggybacks" linear combinations of data from one sub-chunk onto the parity of the second sub-chunk.

During single-node repair, surviving nodes transmit only *half-blocks* (one sub-chunk), reducing network traffic and disk read I/O by 25% to 45% with zero sacrifice in fault tolerance!

Part IV

Compression & Data Integrity

How storage engines shrink bytes and guarantee bit-level fidelity: LZ77 sliding dictionaries, Huffman prefix coding, and SIMD hardware CRC32-C.

13 Dictionary Compression

LZ77 Sliding Window & Token Streams (Snappy / LZ4 Foundation)

Modern high-speed compressors (Snappy, LZ4, Zstandard) are built on the foundational LZ77 (Lempel-Ziv 1977) dictionary algorithm. The compressor maintains a sliding window of recently seen bytes (typically 32KB to 64KB).

As new data enters the lookahead buffer, the compressor searches the sliding window for the longest matching byte sequence. When a match is found, it emits a compact (offset, length) token instead of raw bytes. Decompression is lightning fast because expanding tokens requires only sequential in-memory memcpy() operations without complex tree traversals.

14 Entropy Coding

Huffman Coding: Prefix-Free Binary Trees & Variable-Length Streams

While dictionary compressors eliminate repeated phrases, Huffman Coding eliminates symbol entropy redundancy. David Huffman's algorithm builds a binary tree from bottom to top, pairing least-frequent symbols first.

The resulting binary tree is strictly Prefix-Free: no symbol's binary code is a prefix of another code. Frequent characters (like 'E' or '0') receive short 1- to 3-bit codes, while rare symbols receive longer codes. Standards like DEFLATE (gzip, zlib) pair LZ77 dictionary matches with Huffman entropy coding to achieve maximum density.

15 Hardware Integrity

Hardware-Accelerated Data Integrity: CRC32-C (Castagnoli)

In distributed storage systems managing petabytes of data, Silent Data Corruption (Bit Rot) is an unavoidable physical reality. Drives experience silent media decay without throwing hardware I/O errors.

Storage engines verify block integrity using CRC32-C (Castagnoli Polynomial: 0x1EDC6F41). Castagnoli provides superior Hamming distance properties compared to standard IEEE CRC32. Modern CPUs (Intel SSE4.2 crc32q and ARMv8 CRC extensions) provide dedicated hardware instructions, allowing a single CPU core to verify data integrity at over 30 GB/second!
